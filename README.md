# FM2024 比赛与转会机制逆向调查

研究开始日期：20261014。日期依据：用户首次要求调查 FM2024 比赛胜负、进球与失球的模拟机制。

目标为本机 Steam Windows 桌面版 `24.4.2+2081827`。本仓库保存只读取证与结论，不修改游戏或存档，不包含游戏程序、原始资源归档或存档。

当前研究方向：仅使用 FM24 自身程序和随附资源做静态分析，扩展到全场动作、比赛结果与电脑俱乐部的转会决策。停止游戏内对照实验，第三方编辑器内容不作为后续证据。下列历史运行内存观察仅保留已有来源记录，本轮未新增此类观察。

本阶段研究入口：[一次射门为什么能进球](20261026_射门到进球机制研究.md) · [机制地图](RESEARCH_MAP.md) · [证据索引](EVIDENCE_INDEX.json) · [未解决问题](OPEN_QUESTIONS.md)。当前集中研究属性与上下文如何产生出球、进入正式球轨迹，并经过防守、门线和规则判定成为进球。已补射门族试算提交→正式球复制的顺序，以及预测查询的推进副作用；自然射门完整路径尚未闭合。此前最终比分、数据库引用研究保留，不再作为当前任务的前置工作，不按报告或地址数量验收。

成对方向/距离查询及九处局面记录查询的完整写入范围已在[射门研究](20261026_射门到进球机制研究.md)补证；结论限定索引、存储及对象关系，前置判定也已限定排除历史/引用改写，但缓存未命中时另有按类别筛选的前后记录查询，正向查询可能检查至输入整数时刻加7；另已从准备函数定位球重置状态生产者，并在该状态保持和球员标志条件下覆盖一个完整内层位置判定；已在明确的准备后缀、名单及索引条件下覆盖整个首次缓存，保留同一球、历史和非空比赛引用；已在额外标志/引用数组条件下延伸至准备正常返回，并连接到必先上下文生成器入口；该生成器到模型的保持、入口条件的自然生产与自然射门连续性仍待证明。

复现入口 `python scripts/verify_goal_lifecycle.py` 现在默认核对索引和本地链接，再运行局部算例。加 `--exe <路径>` 会先按 `20261019_fm24_target_identity.json` 核对完整输入身份，身份不同即停止，再复核原始字节和关键直接调用目标；这些检查不代表完整比赛语义验证。验证入口自身的拒绝路径可用 `python scripts/test_goal_lifecycle_verifier.py` 复现。

随附事件资源的110、441和1151分别有2、5、3个变体；此前单变体是冻结算例，不代表该XML默认值。可运行 `python scripts/inspect_match_event_resource.py <simatch.fmf路径>` 核对；资源编号0–1219连续且与0x4c4表长一致；缓存与XML是否对应及实际表槽由该文件成功加载仍是条件，具体见[射门研究报告](20261026_射门到进球机制研究.md)。

当前射门补证使用 `python scripts/verify_shot_execution.py --exe <路径>` 复核原PE指令、关键转移、导入/分派表和限定写入域。已条件连接实际3f候选、A→S初始化/首次物理调用、S→B结构交接及复制后释放；低模型值且已停止的分支覆盖整次射门记录返回。另已条件连接记录时刻命中当前tick→同一B区域5/6输出，并将区域后球查询收敛为派生缓存写入。已由实际caller的非空有序列表推出144415f90无CALL截断复写，并将成功查询后的选定混淆入口接到23bf事件，明确已有1fae历史时的分类和默认时间分流，补同轮门线整数时刻相等及同侧行地址的条件推导；已进一步覆盖M.aa6 bit0取0或1、先前1fae且实际扩容的23bf插入，在双队运动、区域6、球员和阶段条件下接到141a9c120待处理进球入口；其内两次球队更新的副作用仍待证明；仍缺TLS运行保持、自然子步下界、其他历史组合的23bf规则、前置运动更新及后续进球分派。射门后缀、跨tick防守和同一新轨迹的自然生产仍未闭合；具体条件与证据见[射门研究报告](20261026_射门到进球机制研究.md)及索引 `shot_execution`，局部核对不等于自然进球复现。

`python scripts/inspect_preparation_reference_paths.py --exe <路径>` 复用既有目标身份并用GNU objdump重建准备函数本地分支图，检查到清标志末段是否能绕过三处球员引用写入，并列出写入后的待查及必经调用；另复核缓存重算正常返回必经有效位置1、调用者因而跳过第二次重算的条件关系，并检查历史动作0x90在指定读取处如何排除一处球预测查询。输出只证明本地控制流关系；CALL按正常返回处理，尚不证明引用保持、自然可达或进球。记录输出见 `20261030_goal_preparation_reference_paths.json`。

## 射门路径静态复核

`scripts/scan_shot_boundaries.py` 只需要 Python 标准库，读取本次 FM24 PE 布局，输出原始指令模式候选、名称/分派表和常量。候选需与指令边界及消费者核对，不能直接当完整调用图。

```bash
python3 scripts/scan_shot_boundaries.py '/path/to/Football Manager 2024/fm.exe' /tmp/fm24-shot-boundaries.json
```

`scripts/ExportShotCandidates.java` 用已有 Ghidra 导出指定入口的局部伪代码和指令。已使用 Ghidra 12.1.4、JDK 21；参数为输出文件及 `入口:范围结束（不含）`。代码范围见射门证据文件，异常目录范围不等于已恢复全部控制流。复核示例（自行填写工具与游戏路径，先创建临时项目目录）：

```bash
mkdir -p /tmp/fm24-ghidra
"$GHIDRA_HOME/support/analyzeHeadless" /tmp/fm24-ghidra shot_boundaries \
  -import '/path/to/Football Manager 2024/fm.exe' -noanalysis \
  -scriptPath ./scripts -postScript ExportShotCandidates.java \
  /tmp/fm24-shot-local.txt 1443f0420:1443f0d01 1443f0d10:1443f0f58 \
  -deleteProject
```

它会启动静态分析工具并写入临时项目，不运行游戏；单函数反编译超时为 60 秒，保留失败与警告。首次导入大型 PE 可能超过一分钟。该输出属于普通工具静态证据，不是已完成的 REA 原生函数 dossier。

已有匹配的 Ghidra 项目时，可用 `-process fm.exe -noanalysis -readOnly` 替代 `-import ... -noanalysis`，并去掉 `-deleteProject`，复用已导入的 Program；脚本的临时数据库修改会被丢弃。新一轮触球证据采用此方式，另外核对了关键窗口与原文件的一致性，覆盖范围见对应报告。

`scripts/FM24ReadWindows.java` 从已有 Ghidra Program 导出每个指定地址的 96 字节，不运行目标。配合上述只读 `-process` 方式，参数为输出文件和地址，例如 `-postScript FM24ReadWindows.java /tmp/fm24-windows.txt 1453017d0 145305a50`；这些窗口必须与原 PE 对应位置比较，不能当运行时取值。球轨迹报告记录了本轮 29 个窗口及其比对结果。
